# T3.md — RivetOS memory in T3 Code threads

T3 Code is a harness control surface. This kit does **not** auto-inject
memories into the composer. When you lack context, call the RivetOS MCP
tools that the harness loaded.

## Tool mapping

| You want | Call | Notes |
| --- | --- | --- |
| recall | `memory_search` | Default first move. |
| time-bounded recall | `memory_browse` | Prefer `window=` over raw dates. |
| truncated hit | `memory_get_full` | Pass the row id from the hint. |
| store | `memory_append` | Off unless `RIVETOS_MCP_ENABLE_MEMORY_WRITE=1`. |
| summarize | *none* | Compaction worker writes summaries; read with `memory_search` `scope=summaries` or check `memory_stats`. |

Qualified names look like `mcp__rivetos__memory_search` on Claude-style
harnesses. Discover the prefix from the connected `rivetos` server.

If the tools are missing, the harness never loaded this kit — run
`bin/setup-t3code-rivetos-memory.sh` and start a **new** T3 thread.

Completed T3 turns are captured automatically by
`bin/t3code-memory-capture.sh --watch` (run beside `t3 service`). That
sidecar is the write path for every T3 provider. You do not need to call
`memory_append` / `memory_ingest_session` for ordinary turns. Harness-native
capture (Claude hooks, Codex rollouts, OpenCode db) is optional enrichment.
