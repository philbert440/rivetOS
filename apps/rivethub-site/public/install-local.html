Quickstart

One machine. Everything local.

This is the laptop setup: the rh runtime running a standalone node on SQLite, capture and recall for your agent tools, and the desktop app. When it’s done, your tools record their sessions to this machine and can search them.

Point your agent at https://rivethub.io/llms.txt to have it do these steps for you. This page is the manual version.

What you get

Everything on one machine.

  1. One runtime binary. rh is the gateway, memory, workers, tasks, plug-in host and MCP server in one Rust program, with rivethub-migrate beside it for schema migrations. Both come from GitHub releases, checked against SHA256SUMS.
  2. Memory in a SQLite file. rh local creates and migrates ~/.rivethub/memory.sqlite. There is no separate database to run.
  3. Local by default. With --no-lan the node serves plain HTTP on 127.0.0.1:5174. Serving other machines takes gateway TLS, covered in the node guide.
  4. Capture and recall. rh capture hook records each session from your tool’s hooks; an MCP endpoint lets those tools search what was recorded.
  5. The desktop app on Linux. A native app, built from source with one script.

Requirements

Linux on x86_64 or aarch64 with glibc 2.35 or newer, or macOS (one universal build) · curl and tar · on Windows, the Linux build under WSL.

Install

Install rh.

Download the newest release for your platform, check it against the release’s SHA256SUMS, and put both binaries in ~/.local/bin, which needs to be on your PATH:

on your laptop 
$ REPO=https://github.com/philbert440/rivethub-runtime
$ TAG=$(curl -fsSL "https://api.github.com/repos/philbert440/rivethub-runtime/releases?per_page=1" | grep '"tag_name"' | cut -d'"' -f4)
$ TARGET=x86_64-unknown-linux-gnu
$ ARCHIVE="rh-${TAG#v}-$TARGET.tar.gz"
$ curl -fsSLO "$REPO/releases/download/$TAG/$ARCHIVE"
$ curl -fsSLO "$REPO/releases/download/$TAG/SHA256SUMS"
$ grep " $ARCHIVE\$" SHA256SUMS | sha256sum -c -
$ tar -xzf "$ARCHIVE" rh rivethub-migrate
$ install -d ~/.local/bin && install -m 0755 rh rivethub-migrate ~/.local/bin/
$ rh version

Set TARGET to aarch64-unknown-linux-gnu on ARM Linux or universal-apple-darwin on macOS. macOS checks the sum with shasum -a 256 -c - in place of sha256sum -c -.

The newest release is a beta: every merge publishes one. How releases work →

Run a node

Start it, then check it.

terminal 
$ rh local --no-lan --ensure --wait 30
$ curl -s http://127.0.0.1:5174/healthz

--ensure starts the node in the background unless one already answers, and waits up to --wait seconds for it; drop it to run the node in the foreground. Its output goes to ~/.rivethub/logs/local.log. The health check answers {"ok":true,…} with the node’s name and version.

The first run writes ~/.rivethub/config.yaml. Pass --no-lan on that run: without it the file records 0.0.0.0, and the node refuses an off-loopback bind until gateway TLS is set up. Later runs read the file, so plain rh local --ensure --wait 30 is enough.

There is no browser interface at http://127.0.0.1:5174/: you use the node through your agent tools and the desktop app.

What it connects

Connect your agent tools.

Each tool needs two things: recall, an MCP server it can search, and capture, a hook that records its sessions to your node.

Recall

Give the node an MCP endpoint. Append this to ~/.rivethub/config.yaml with a token of your own (openssl rand -hex 32 makes one; the endpoint refuses to start without it), then restart the node: rh stop, a few seconds’ wait, and rh local --ensure --wait 30.

~/.rivethub/config.yaml 
transports:
  mcp:
    host: 127.0.0.1
    port: 5700
    auth_token: <token>

Then register it with each tool. For Claude Code:

terminal 
$ claude mcp add --transport http --scope user rivethub http://127.0.0.1:5700/mcp --header "Authorization: Bearer <token>"

New sessions get memory_search, memory_browse, memory_stats, memory_get_full, memory_tags, wiki_search and wiki_read, plus delegation and the plug-in creator. A session that was already open won’t see the new server.

Capture

Every tool’s hook runs rh capture hook. It reads the hook’s payload on stdin, posts the session to your node, and always exits 0, so a capture problem never interrupts the tool. For Claude Code, add these hooks to ~/.claude/settings.json:

~/.claude/settings.json 
{
  "hooks": {
    "UserPromptSubmit": [{ "hooks": [{ "type": "command", "command": "$HOME/.local/bin/rh capture hook" }] }],
    "Stop": [{ "hooks": [{ "type": "command", "command": "$HOME/.local/bin/rh capture hook" }] }],
    "SubagentStop": [{ "hooks": [{ "type": "command", "command": "$HOME/.local/bin/rh capture hook" }] }],
    "SessionEnd": [{ "hooks": [{ "type": "command", "command": "$HOME/.local/bin/rh capture hook" }] }]
  }
}
How each tool records to your node
Agent toolHook commandEventsWhat it reads
Claude Coderh capture hookUserPromptSubmit, Stop, SubagentStop, SessionEndThe hook payload and the session transcript.
Grok Buildrh capture hook --harness grok-buildStop, PreCompact, SessionEndThe session’s updates.jsonl under ~/.grok.
Codexrh capture hook --harness codexStop, SessionEndThe session rollout under ~/.codex/sessions.
opencoderh capture hook --harness opencodesession.idle, from an opencode plug-inThe session in opencode’s database.
DeepSeek Harnessrh capture hook --harness dshturn/end, from a dsh plug-inThe session log under ~/.dsh.
Kimi Code, HermesThe integration kits in rivetOS integrations/.

The Codex, opencode and dsh options arrive in the release after v0.7.0; rh capture hook --help lists what your build supports. No ready-made opencode or dsh plug-in is published yet: yours runs the hook with {session_id, hook_event_name, cwd} on stdin. If the node is down when a hook runs, the batch waits in ~/.rivethub/capture-spool and goes out with the next capture. Each tool logs its captures in ~/.rivethub, for example claude-capture.log. Desktop app

Build the desktop app.

The RivetHub desktop app is native Rust, built from source on Linux. You need Rust through rustup (the repository pins its toolchain) and the development packages for Wayland/X11, Vulkan, fonts and WebKitGTK 4.1, which plug-ins’ web panels run in. On Debian or Ubuntu:

Debian / Ubuntu 
$ sudo apt install clang libxkbcommon-dev libxkbcommon-x11-dev libwayland-dev libvulkan-dev libfontconfig-dev libfreetype-dev libxcb1-dev libasound2-dev libssl-dev libwebkit2gtk-4.1-dev pkg-config

With pacman, the WebKitGTK package is webkit2gtk-4.1. Then build and install it into ~/.local, with a menu entry:

terminal 
$ git clone https://github.com/philbert440/rivethub-desktop
$ cd rivethub-desktop
$ packaging/linux/install.sh

The app connects to https://127.0.0.1:5174 and trusts the CA in ~/.rivethub/step-root.crt. RIVETHUB_URL and RIVETHUB_CA point it elsewhere. The app reads a CA file even for a plain-HTTP node, so for the standalone node above, start it with RIVETHUB_URL=http://127.0.0.1:5174 RIVETHUB_CA=/etc/ssl/certs/ca-certificates.crt rivethub-desktop. A device certificate in ~/.config/RivetHub/mtls/ (RIVETHUB_DEVICE_DIR) identifies it to nodes that ask for one. Starting chats and terminals from the app also needs gateway.terminal.enabled: true in the node’s config; the app tells you when it’s off. More in the desktop README.

There’s no desktop app for macOS or Windows yet. On Omarchy, the app can follow your theme: RivetHub on Omarchy →

Your phone

Check in from your phone.

The Android app is built from source in the rivetOS repository (./gradlew :app:assembleDebug, with JDK 21 and the Android SDK). To pair it, open the desktop app’s Settings → Devices → Pair a phone, choose Show pairing code, and scan it from the phone with Scan pairing QR.

Pairing issues the phone a certificate, so the node needs a certificate authority; on a standalone node without one, the desktop says pairing isn’t available. Set one up with the server guide. There is no iPhone app.

How memory works

Recorded for you. Searchable by your tools.

Capture saves as you work

Prompts, replies and tool calls from a connected tool are written to your node as the session goes. The record stays on your machine.

Recall brings it back

Inside a session, a connected tool can search the node for earlier work and answer with it. Full-text and fuzzy search work from the first session. Semantic search and summaries need an OpenAI-compatible embedding endpoint and a model that you configure; they process what you send them, so choose where they run.

Add another machine

Grow when you’re ready.

A standalone node is complete on its own. To share one memory across machines, run a Postgres datahub and nodes that use it; the server guide walks through the layout. Your memory comes along: rh memory export writes it to one file, and rh memory import reads it on the other side (try --dry-run first).

Everyday commands

Day-to-day commands.

Check the node

terminal 
$ curl -s http://127.0.0.1:5174/healthz
$ rh db status

Stop and start

terminal 
$ rh stop
$ rh local --ensure --wait 30

Give the node a few seconds to exit after rh stop before starting it again.

Update

terminal 
$ rh update --channel beta --no-restart

The update checks the archive against SHA256SUMS, migrates your memory, swaps both binaries and keeps the old ones as rh.previous and rivethub-migrate.previous. Then stop and start the node. Use the beta channel for now: the stable channel still resolves v0.1.4, which refuses the current schema. Releases →

Back up your memory

terminal 
$ rh memory export --out rivethub-memory.gz

Uninstall

Stop the node, then delete ~/.local/bin/rh and ~/.local/bin/rivethub-migrate. ~/.rivethub holds your config and memory; back it up before you remove it. Remove your tools’ capture hooks and MCP entries, and the desktop app’s files in ~/.local.

Troubleshooting

If something sticks.

“refusing to bind 0.0.0.0”

The first rh local ran without --no-lan, so the config records 0.0.0.0. Set gateway.host to 127.0.0.1 in ~/.rivethub/config.yaml, or give the gateway TLS.

Port 5174 is busy

Check what is using it. To move the node, set gateway.port in ~/.rivethub/config.yaml; --port changes a single run only.

rh doctor or rh mcp asks for runtime, agents and providers

Those commands check a full node, which runs agents; a standalone node doesn’t need those sections. Check it with the health route and rh db status, and use the HTTP MCP endpoint above for recall: rh mcp on its own needs a Postgres-backed node.

A session isn’t showing up

Check that the node answers, then the tool’s capture log in ~/.rivethub and any batches waiting in ~/.rivethub/capture-spool. Hooks and MCP servers load when a session starts, so start a new session after changing them.
