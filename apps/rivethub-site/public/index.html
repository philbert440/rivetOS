The problem

Not a hosted black box.

A lot of "agent memory" lives inside one chat product you do not run. It remembers for that app, on its terms, and forgets the moment you switch tools.

RivetHub is different. The record sits on your side — a laptop, a server you pick, or a hosted database you can export from any time. Your model providers still see the prompts you send them; that is how those tools work. RivetHub keeps the record of what your agents did, so you and they can find it again.

I · RivetOS

The runtime that remembers for every tool.

RivetOS is the engine underneath: a personal agent runtime and memory plane. It plugs into the tools already on your PATH over MCP and quietly does three things.

  1. capture

    Sessions save themselves.

    As you work, each session lands in a Postgres-backed store on your hub: prompts, tool calls, results — from whichever supported tool you are in. Nothing to remember to write down.

  2. recall

    The next session knows.

    Connected tools search the hub before they answer. Brand-new session, different tool, no recap paste. Full-text and fuzzy search work from the first session; semantic search is an optional embedding endpoint you point it at.

  3. source

    Answers you can check.

    Every hit opens the original conversation with its tool calls attached. Not a mystery summary — the actual exchange, so you can read what was said.

II · RivetHub

The hub you run it on.

RivetHub is how RivetOS gets onto your machines: the installers, the desktop and Android apps, and a UI for browsing everything your agents have done. Same repo, one product. Two ways to run it.

Path A · start here

Local only

One machine runs the hub and your agents. The installer sets up the hub, wires capture and recall into the supported tools it finds, and leaves you at https://localhost:5174.

on your laptop
$ curl -fsSL https://get.rivethub.io/local.sh | bash

Path B · always on

Dedicated data hub

Put the hub on a Debian or Ubuntu server, then enroll agent nodes over SSH. Every machine writes to — and recalls from — the same memory.

on the node, once the datahub is up

III · Rivet Cloud

Or let us keep the box running.

Rivet Cloud is hosted memory at rivetos.cloud. Your agents still run where they run today, on the subscriptions you already pay for. We store, embed and summarize what they capture — and you can walk away with all of it.

  • Nothing to operate. No Postgres to tune, no embedding model to host, nightly backups kept for 14 days.
  • Same RivetOS on your side. Install from RivetHub, then paste the connect command from your dashboard.
  • Export any time. A portable Rivet archive you can import into cloud or self-hosted RivetOS.

Asked often.

What is RivetHub?

The self-hosted hub and human UI for the RivetOS runtime: a personal AI agent runtime and memory plane. It records sessions, tool calls, and outputs from connected tools, and makes that history searchable by you and by those tools over MCP.

Same repo as RivetOS?

Yes. RivetHub is the distro and front door for philbert440/rivetOS. Docs live at rivetos.dev; this site gets a hub running.

Is this SaaS?

No. Self-hosted by default. Rivet Cloud is a separate, optional hosted-memory service with export — your agents still run on your machines either way.

Where does data go?

On your hub. Providers still process the prompts you send them. Cloud embedding or compaction only happens if you configure it, or if you choose Rivet Cloud.

Do I need an embedding model to start?

No. Search works out of the box. Semantic search is an optional upgrade that uses an embedding endpoint you choose and configure on the hub.

Can I run the hub on Windows?

The hub installer supports Linux and macOS. On Windows, the desktop app connects to a hub running elsewhere — your Linux server or another machine on the network.
