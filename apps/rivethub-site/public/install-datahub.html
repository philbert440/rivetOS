install · datahub

Run a datahub

← Server setup overview

The datahub holds the shared memory: Postgres with pgvector, the memory schema that rivethub-migrate keeps current, and the memory workers that embed, summarize, categorize and build the wiki. Nodes connect to it; the certificate authority usually lives beside it.

Requirements

  • Postgres 16 with the vector (pgvector) and pg_trgm extensions. On Debian or Ubuntu, postgresql-16 and postgresql-16-pgvector from the PGDG repository.
  • Linux on x86_64 or aarch64 (glibc 2.35 or newer) with systemd for the workers.
  • Superuser access to the database once, for the steps below, and Node.js once, to install the job queue with npx.
  • For semantic search and summaries, an OpenAI-compatible embedding endpoint and a model for the summarizer.

database

Create the database

As a superuser, create a role and a database it owns, and the two extensions:

psql, as a superuser 
CREATE ROLE rivethub LOGIN PASSWORD '<password>';
CREATE DATABASE rivethub OWNER rivethub;
\c rivethub
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;

once per database

The one-time superuser steps

From rh 0.7.1, every memory table enforces row-level security, including for its owner, so each person sees only what is theirs or shared with them. Postgres lets search and capture keep using their indexes under those policies only when the operators they filter with are marked LEAKPROOF, and only a superuser can mark them. Run this once in the memory database:

psql rivethub, as a superuser 
ALTER FUNCTION ts_match_vq(tsvector, tsquery) LEAKPROOF;
ALTER FUNCTION textlike(text, text) LEAKPROOF;
ALTER FUNCTION texticlike(text, text) LEAKPROOF;
ALTER FUNCTION textregexeq(text, text) LEAKPROOF;
ALTER FUNCTION texticregexeq(text, text) LEAKPROOF;
ALTER FUNCTION jsonb_object_field_text(jsonb, text) LEAKPROOF;

Migrations 0044 and 0051 mark these themselves when they run as a superuser. Run as the owner instead, they stop until the operators are marked; rivethub-migrate reports only that applying the migrations failed, and the Postgres log has the statement.

Large stores: migration 0051 adds an index over every message’s capture event id. To keep writes flowing, build it ahead of the upgrade without a lock; the migration then leaves it as it is:

psql rivethub 
CREATE INDEX CONCURRENTLY IF NOT EXISTS rh_messages_event_id
    ON rh_messages (conversation_id, (metadata ->> 'event_id'))
    WHERE (metadata ->> 'event_id') IS NOT NULL;

job queue

Install the job queue

The workers and tasks share graphile-worker’s graphile_worker schema, which rh does not create. Install it once, as the owner role; without it every worker exits with “the graphile_worker schema is absent on this database”:

as the owner role 
$ npx graphile-worker@0.17 --schema-only -c "$RIVETHUB_PG_URL"

migrate

Migrate before anything starts

Gateways and workers never migrate the schema themselves. Run rivethub-migrate postgres on a fresh database and after every upgrade, before starting or restarting any gateway or worker against it. With the connection string in RIVETHUB_PG_URL (or a config whose memory.postgres names it):

on the datahub 
$ rivethub-migrate postgres --config ~/.rivethub/config.yaml
$ rivethub-migrate status postgres --config ~/.rivethub/config.yaml

--url takes the connection string directly, and rh db migrate and rh db status do the same from rh. A database that the TypeScript RivetOS runtime used is adopted in place: its tables are renamed to rh_*, with ros_* views left behind so the old workers keep running while you switch. Take a pg_dump first. If that database holds conversations from more than one owner, migration 0042 asks which person owns the older, unowned rows: add ?options=-c%20rh.store_owner%3D<user> to the connection URL for that run.

workers

Run the memory workers

Each role is one process: embedder, summarizer, categorizer and wiki-builder, or all in one. The workers read the node config (the summarizer and categorizer use the default agent’s provider) plus an embedding endpoint:

worker config, memory section 
memory:
  postgres:
    connection_string: ${RIVETHUB_PG_URL}
    embed_endpoint: http://127.0.0.1:8080/v1
    embed_model: <embedding model>
on the datahub 
$ rh worker --role embedder --check
$ rh worker --role embedder

Run one systemd unit per role, each with ExecStart=… rh worker --role <role> and EnvironmentFile pointing at the file that holds RIVETHUB_PG_URL; rh start does not start Postgres workers for you. The wiki builder also needs RIVETHUB_WIKI_EXTRACTION=1, and RIVETHUB_WORKER_CONCURRENCY sets how many jobs each worker takes at once (four by default). rh memory queue-status shows the queue. A complete unit file and wiki housekeeping are in Operating RivetHub on Postgres.

certificate authority

The certificate authority

Mesh, device and agent certificates come from step-ca, which you bootstrap and run yourself; rh is its client and never holds the CA key. With the step CLI installed, rh ca mints one-time tokens for the names in your operator roster, revokes certificates and publishes the revocation list:

on the CA host 
$ rh ca status --ca-url https://ca.example:9000 --root root.pem
$ rh ca token node node-a --ca-url https://ca.example:9000 --root root.pem --provisioner-password-file provisioner.pass --roster roster.txt
$ rh ca crl --ca-url https://ca.example:9000 --root root.pem --crl-out crl.pem

Enrolling a node is in the node guide; the design is in PKI.

backups

Back it up as a superuser

on the datahub 
$ sudo -u postgres pg_dump -Fc -d rivethub -f rivethub.dump

Because the tables force row-level security, pg_dump run as the owner stops with query would be affected by row-level security policy. Run it as a superuser. Restore as a superuser too, into a database owned by the same role, then run the six ALTER FUNCTION statements on it before starting anything: the LEAKPROOF marks belong to each database and don’t travel in a dump.

Retired. The datahub.sh installer, the rivethub-hub helper and rivet-ca.sh set up the TypeScript RivetOS datahub. A datahub they built keeps its Postgres: adopt it with rivethub-migrate postgres as above and follow moving the memory workers.
