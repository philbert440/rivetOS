Install a node

← Server setup overview

A node runs rh under systemd against a shared Postgres memory: the gateway your apps talk to, the task engine your agents run in, and MCP for the tools on that machine. Set up the datahub first; a single machine with no datahub is the Quickstart.

Requirements

  • Linux on x86_64 or aarch64, glibc 2.35 or newer, with systemd.
  • A Postgres memory database that rivethub-migrate postgres has brought up to date, reachable from this machine.
  • For each agent that drives a CLI harness, its ACP adapter on the node: for Claude Code, @agentclientprotocol/claude-agent-acp. Without it the provider starts degraded and says so.

install

Install the binaries

Install rh and rivethub-migrate into ~/.local/bin as the Quickstart shows, as the user the node will run as.

configure

Write the configuration

The node reads ~/.rivethub/config.yaml. A node needs runtime, agents and providers, and the memory database. Keep the connection string out of the file: ${RIVETHUB_PG_URL} is read from the environment, and the service reads ~/.rivethub/.env (mode 0600).

~/.rivethub/config.yaml 
runtime:
  workspace: /home/user/work
  default_agent: claude
agents:
  claude:
    provider: claude-cli
providers:
  claude-cli:
    model: sonnet
memory:
  postgres:
    connection_string: ${RIVETHUB_PG_URL}
gateway:
  host: 127.0.0.1
  port: 5174
~/.rivethub/.env 
RIVETHUB_PG_URL=postgres://rivethub:<password>@<datahub>:5432/rivethub

Then check it without starting anything:

on the node 
$ rh config validate
$ rh gateway --check
$ rh doctor

rh doctor checks the config, the state directory, disk space and the memory schema, and never migrates. Every key, including the terminal and allowed_origins gateway settings, is in the CLI reference.

run

Run it under systemd

on the node 
$ rh service init
$ rh service start
$ rh service status
$ rh status

rh service init writes rivethub.service: a system unit when run as root, a user unit otherwise (it tells you whether lingering is on). The unit runs rh start, which supervises the gateway, the task engine and, when transports.mcp names a host or socket, the MCP server. rh logs follows its journal and rh stop stops it.

tools

Connect the tools on this node

Recall on a Postgres node can use the stdio MCP server, rh mcp, with the node’s environment. For Claude Code:

on the node 
$ claude mcp add --scope user rivethub -- bash -c 'set -a; . "$HOME/.rivethub/.env"; set +a; exec "$HOME/.local/bin/rh" mcp'

Capture uses the same rh capture hook commands as the Quickstart; the hook finds this node’s gateway from its config.

mesh

Certificates and the mesh

A gateway that serves other machines needs TLS: gateway.tls_cert and gateway.tls_key (or RIVETHUB_TLS_CERT and RIVETHUB_TLS_KEY), plus gateway.tls_ca to require client certificates. Certificates come from step-ca, which you run outside RivetHub (see the datahub guide). Nodes and agents hold 7-day certificates and renew them themselves; keys are generated on the holder and never leave it.

On the CA host, mint a one-time token for the node from your roster. On the node, enroll with that token, then keep the certificate renewed:

on the CA host 
$ rh ca token node node-a --ca-url https://ca.example:9000 --root root.pem --provisioner-password-file provisioner.pass --roster roster.txt
on the node 
$ rh cert renew --principal spiffe://rivet.mesh/node/node-a --ca-url https://ca.example:9000 --trust-root root.pem --token-file token --once
$ rh cert renew --principal spiffe://rivet.mesh/node/node-a --ca-url https://ca.example:9000 --trust-root root.pem

The key and certificate land in ~/.rivethub/tls/. Without --once the command stays running and renews at two thirds of each certificate’s life, so it belongs in its own systemd unit. rh mesh enroll does the token and the first certificate in one step and records the node; the roster format and every flag are in the certificate commands and PKI docs.

mesh 
$ rh mesh list
$ rh mesh ping
$ rh mesh status

update

Update one node, or all of them

on any node 
$ rh update --channel beta
$ rh update --channel beta --mesh

An update checks the release archive against SHA256SUMS, runs the new rivethub-migrate against the configured database, swaps both binaries (keeping *.previous copies) and restarts the unit. --mesh then runs the same update over SSH on every node in mesh.json, pinned to the release installed here. Use the beta channel for now: stable still resolves v0.1.4. Releases →

from rivetos

Moving a RivetOS node

A node running the TypeScript RivetOS runtime moves with rivetos migrate-to-rivethub: it installs rh, moves ~/.rivetos to ~/.rivethub, brings memory over and swaps rivetos.service for rivethub.service, with --rollback to go back. It downloads the newest release itself and checks it against SHA256SUMS; --binary installs a build of your own instead. Run rivetos update first so the CLI has the current download. The whole procedure is in Migrating to RivetHub.

Retired. The node.sh installer, the rivethub-hub helper and rivet-ca.sh belong to the TypeScript runtime. rh enrolls through step-ca instead.
